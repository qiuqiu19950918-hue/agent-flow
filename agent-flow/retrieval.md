# 📡 检索子 Agent 规范（Retrieval）

## 角色
负责"定位代码"，不做修改、不跑命令。

## 首选与兜底
- **首选**：`code-retriever` —— 项目代码检索专家，支持两类起点：
  - **起点①·pmem anchor（可选，需项目装有 project-memory skill）**：主Agent 已从 pmem 图谱提取精确 anchor（file:symbol），code-retriever 从 anchor 出发，沿调用链/依赖链做广度搜索（参照原生 Explore 机制：读 excerpts 不读全文、只定位不审查、返回切片不 dump）。pmem 的实体/关系/规则作为"硬包含"信息直接进蓝图，不靠检索。
  - **起点②·关键词（无 pmem 时）**：按文件列表 + 关键词定位；精准无结果则切 broad fan-out（Glob 扫命名 + Grep 宽匹配）。
  - **结果不足**：code-retriever 判断结果明显不足时，回报标注"结果不足建议"，主Agent 决定是否转交 Explore。

  （工具：Read, Grep, Glob）
- **兜底**：`Explore` —— 只读搜索 Agent，仅在 code-retriever 结果不足或 L1 失败后转交。它相比 code-retriever **多出 `Bash` / `WebSearch` / `WebFetch`**（可跑只读 shell 命令、可联网），故额外适用于：用 shell 管道做复杂文件筛选（如 `find ... | wc -l`）、或 code-retriever 搜不全时的补充盲扫。（工具：Read, Bash, WebFetch, WebSearch, TodoWrite）

> **能力对照**：纯代码 / 目录 / 配置的检索与扫描，`code-retriever` 的 Read/Grep/Glob 已完全胜任。只有需要 "**shell 管道**" 或 "**code-retriever 结果不足的补充**" 时，`Explore` 才具有不可替代价值。
>
> **⚠️ 联网检索不在本文件范畴**：查阅线上文档/API/技术资料等**联网检索**，首选 `cmd-executor`（见 `command.md` 联网检索升级链），L1 失败转交 `general-purpose`，不走 code-retriever / Explore。本文件的"首选/兜底"仅针对**本地代码检索**。
>
> **⚠️ pmem 为可选集成**：若项目未安装 project-memory skill，检索直接走"起点②·关键词"，不影响 agent-flow 正常运行。pmem 起点仅在项目装有 pmem 且主Agent 蓝图含 [检索起点] 字段时启用。

## 主 Agent 调度它时必须提供
1. **检索目的**（如："找到处理登录的 controller 以便后续修改入参校验"）。
2. **起点**（二选一）：
   - 若项目装有 pmem：**pmem anchor 列表**（file:symbol）+ [项目上下文]（实体/关系/规则，硬包含）。
   - 若无 pmem：**文件列表 / 目录范围 + 关键词 / 符号名**。
3. **广度提示**（可选，如"very thorough，沿调用链扩搜"）。

## 输出契约（分层返回）

检索子 Agent 的返回必须分为三个明确段落，区分 pmem 背书内容与子 Agent 推测内容，让主 Agent 差异化对待：

```
[角色] code-retriever / Explore
[模型] <自身模型名>

[PMEM 命中] （仅当主 Agent 在调度 prompt 里给了 pmem anchor/实体时才填）
  pmem 图谱涉及的实体/关系/规则的代码详情。每条带 path:line + 完整关键片段。
  这部分是图谱背书的高可信内容，主 Agent 默认采信。
  - <实体名/关系描述>
    📍 path/to/file.java:42-58
    （完整的关键代码片段，不截断）
    📌 pmem 偏差（可选）：若代码已不在 anchor 处，标注"pmem偏差:<具体不符>"

[扩展发现] （子 Agent 自行沿调用链/依赖链扩搜的内容）
  ⚠️ 这部分是子 Agent 推测的相关内容，主 Agent 默认怀疑，需复核后采信。
  仅返回"摘要 + 路径"，不返回完整代码片段（避免污染主上下文）。
  - <方法/类/字段简述>
    📍 path/to/file.java:行号区间
    💡 相关性说明：<一句话>
    🔍 详情按需取用（主 Agent 判定需要时再 Read）

[结论] 找到 / 未找到 / 部分找到
[证据强度自评] 高（每条结论都有 path:line + 片段）/ 中 / 低
[完备性自评] 查了 N 文件/M 匹配，详述 K 个
[探查清单] （完备性校验用，见 §完备性校验）
  - Grep "<关键字>" → 命中 N 个文件 / M 行；详述了 K 处；未详述: <列出>
```

### 分层规则
| 内容类型 | 归属段落 | 返回详细度 | 进主上下文 |
|---|---|---|---|
| 主 Agent 在 prompt 里指明的 pmem anchor/实体 | `[PMEM 命中]` | **完整片段**（不截断） | ✅ 进（高可信，主 Agent 决策需要） |
| 子 Agent 沿调用链扩搜的相关方法/类 | `[扩展发现]` | **仅摘要+路径** | ⚠️ 只进摘要（详情按需取） |
| 子 Agent Grep 到但未详读的匹配 | `[探查清单]` | **仅计数+文件名** | ✅ 进（完备性判断用） |

> **检索类不套用"成功回摘要"**（见 `SKILL.md` §5.3）：检索结果是信息型产物，是主 Agent 后续工作的原料，**必须以"精确切片"（path:line + 关键片段）形式留在主 Agent 上下文**，不能压缩为"找到了"这种摘要（无价值），也不能回整文件（上下文爆炸）。token 控制**靠派发时给清范围/关键词/要几行**，让子 Agent 切得准。
>
> **pmem 偏差标注（pmem 起点任务专属）**：若使用 pmem anchor 起点，code-retriever Read anchor 时发现代码已不在该处（anchor 失效），必须在回报标注"pmem偏差:<具体不符>"，主 Agent 收到后触发 pmem 归档更新。

### 边界情况
- **无 pmem 起点**（项目未装 pmem，或主 Agent 走"关键词起点"）：省略 `[PMEM 命中]` 段，所有内容归 `[扩展发现]`，主 Agent 对全部返回按"待复核"处理。
- **pmem 图谱不全**（图谱缺实体）：子 Agent 在 `[扩展发现]` 里发现的、pmem 未记录的实体，额外标注 `⚠️ pmem 未记录`，提示主 Agent 触发 pmem 归档。
- **全量读取任务**（如 pmem migrate 需完整文件内容做转换）：主 Agent 在调度 prompt 里明确要求"全量读取"，此时 `[PMEM 命中]` 返回完整结构化内容（非摘要），区别于普通"定位"任务。

## 主 Agent 按需二次取用

主 Agent 收到分层返回后：
1. **直接采用** `[PMEM 命中]` 的完整片段（高可信）。
2. **阅读理解** `[扩展发现]` 的摘要，形成全局认识。
3. **按需决策**：哪些扩展详情是制定方案必需的？
4. **取用方式**（二选一）：
   - 主 Agent 自己 `Read` 该文件的具体行（适合只需 1-2 处定点详情）。
   - 派检索子 Agent 二次检索取回详情（适合需多处、或需沿调用链继续扩搜）。

| 扩展内容特征 | 推荐取用方式 | 理由 |
|---|---|---|
| 只需 1-2 处定点详情，已知精确行号 | 主 Agent 自己 Read | 1 次 Read 比 1 次调度往返便宜 |
| 需沿调用链继续扩搜 | 派检索子 Agent | 扩搜是子 Agent 的活，避免主 Agent 陷入检索泥潭 |
| 需理解复杂逻辑（多文件交叉）| 派检索子 Agent | 多文件交叉适合子 Agent 独立上下文 |
| 详情体量大（>2000 字符）| 派检索子 Agent 返回结构化摘要 | 避免大块内容进主上下文 |

### 取用循环限制（重要）
**最多 2 轮二次取用**。第 1 轮首次检索；第 2 轮看摘要后取扩展详情；第 3 轮（最多）补充取用；第 4 轮起禁止，无论是否完备进入执行阶段靠反馈兜底。

> 原则：检索不能无限精细化。3 轮还不全，说明任务需拆分或 pmem 需补建，而非继续检索。

## 主 Agent 上下文卫生

### 红线规则
- ❌ **主 Agent 禁止 Read 超过 2KB 的文件做"理解"用途** → 下放检索子 Agent，要求返回结构化内容。
- ✅ 主 Agent 可 Read 小文件（<2KB）做定点复核。
- ✅ 主 Agent 可对子 Agent 已读文件做**有依据的复核**（破绽驱动，非默认不信，见 `verification.md`）。
- ❌ 主 Agent 最终回复禁止复述子 Agent 报告原文 → 只给用户结论，不复述。

### 依据
主 Agent 上下文是成本大头（实测占总 token 67%）。主 Agent 每直接 Read 一个大文件，该内容在后续所有调用中重复计入。改为子 Agent 读+返回摘要，子 Agent 成本仅主 1/10。

## 完备性校验

主 Agent 收到检索返回后，必须走完备性校验（详见 `verification.md`）：
- **需求覆盖度检查**：返回能否满足任务需求（发现内部缺口）。
- **pmem 图谱交叉验证**（仅 pmem 场景）：返回覆盖了图谱相关实体吗。
- **结构完整性探查**：基于 `[探查清单]` 对比匹配总数 vs 详述数。
- **执行反馈兜底**（事后）：执行阶段让缺漏自然暴露。

> ⚠️ 主 Agent 无法 100% 保证完备（信息不对称悖论）。默认子 Agent 返回可能不完备，主动寻找遗漏信号（图谱邻居未覆盖、Grep 匹配数不一致、返回出现"等/其他"字样）。

## 何时升级（L1→L2）
- 返回空结果、找不到符号、或工具报错 → 主 Agent **重写更具体的 prompt 重试 1 次**（可换用 code-retriever 自身的 broad fan-out：Glob 扫命名 + Grep 批量搜内容）。
- 仍失败 → 转交 `Explore`，利用其额外的 `Bash`/`WebSearch`/`WebFetch`（联网或 shell 管道）突破本地文件检索的局限。
