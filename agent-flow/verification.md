# 验收协议（可信度判定 + 完备性校验 + 复核决策树）

> 本文档定义**检索类子 Agent 结果的验收机制**：可信度判定、完备性校验、主 Agent 复核决策树。
> 配套阅读：`retrieval.md`（分层返回 + 上下文卫生）、`SKILL.md` §1.5（三类差异化对待）、§4.4（复核权）。

## §0 适用范围（重要）

**本协议仅适用于检索类子 Agent（code-retriever / Explore）。** 执行类（code-executor）和命令类（cmd-executor）的结果有客观验证信号（编译/退出码），主 Agent 信状态即可（信任委托），**无需走本协议**。

> 这是三类差异化对待的核心：检索类结果不可自验证，必须主 Agent 验收；执行/命令类可自验证，信任委托。

---

## §1 可信度判定（四维检查）

主 Agent 收到检索子 Agent 的分层返回后，依次检查 4 个维度：

### 维度 ①：完整性
**检查**：子 Agent 是否返回了 prompt 要求的所有项？
- ✅ 达标：prompt 要求的每项都有对应返回。
- ❌ 不达标：有要求项未返回 → 记录缺口，触发补充检索。

### 维度 ②：自洽性
**检查**：返回内容内部有无矛盾（计数不符、描述前后矛盾）？
- ✅ 达标：计数一致、描述不矛盾。
- ❌ 不达标 → 定点复核矛盾点。

### 维度 ③：证据强度
**检查**：关键结论是否都带 path:line + 原文片段？
- ✅ 高：每条关键结论都有 path:line + 完整片段。
- ⚠️ 中：有 path:line 但片段不全。
- ❌ 低：只有结论没证据（纯文字断言）→ 关键结论需定点复核。

### 维度 ④：与已知信息一致性
**检查**：与主 Agent 已掌握的信息（pmem 图谱 / 前轮结论 / 用户明确陈述）是否冲突？
- ✅ 一致：与已知信息吻合。
- ❌ 冲突 → 定点复核（注意：已知信息也可能过时，不盲目信图谱）。

### 分层可信度（配合分层返回）
| 返回层次 | 默认可信度 | 四维检查严格度 |
|---|---|---|
| `[PMEM 命中]` | 高（图谱背书） | 只查 ④（与已知一致性），其余默认通过 |
| `[扩展发现]` | 待定（子 Agent 推测） | **全查四维**，任一不达标触发复核 |
| `[探查清单]` | 客观（Grep 计数） | 不查（原始数据，用于完备性判断） |

## §2 完备性校验

### 2.1 诚实前提：无法保证 100% 完备

> **主 Agent 无法在事前 100% 可靠判断子 Agent 返回是否完备。** 这是信息不对称悖论——主 Agent 不知道"全集"（否则不用派子 Agent），却要判断"子集够不够"。

本协议提供的是**"提高发现缺漏概率"的策略组合**，不是"消除缺漏"的银弹。务实组合：事前尽量发现 + 事后执行反馈兜底。

### 2.2 四种完备性校验策略

#### 策略 A：需求覆盖度检查（最常用，发现内部缺口）
**逻辑**：不看"返回了多少"，看"返回的能否满足任务需求"。
- ✅ 能发现：返回内容内部的缺口（需求某环节没覆盖）。
- ❌ 发现不了：需求定义本身的缺口（主 Agent 没想到的隐式环节）。

#### 策略 B：pmem 图谱交叉验证（图谱背书场景）
**逻辑**：用 pmem 图谱的拓扑关系反推"应该涉及哪些实体"。
- ✅ 能发现：子 Agent 漏掉的相关实体（图谱已记录的）。
- ❌ 发现不了：图谱本身未记录的关系。
- **注意**：只能发现"实体级"缺漏，发现不了"某实体的某方法"级缺漏。

#### 策略 C：结构完整性探查（基于探查清单）
**逻辑**：利用子 Agent 返回的 `[探查清单]`，对比"匹配总数" vs "详述数"。
- 任务关心"所有涉及 X 的代码" → 未详述处是疑点 → 触发补充检索。
- 任务只关心"入口+统计" → 已详述处覆盖 → 判定完备。

主动探查手段：
| 探查手段 | 能发现 | 成本 |
|---|---|---|
| 要求子 Agent 返回 Grep 总匹配数 vs 详述数 | 漏返回的匹配 | 低 |
| 要求子 Agent 先返回"完整清单"再详述 | 隐藏的未返回项 | 中 |
| 主 Agent 自己跑一次广度 Grep/Glob | 涉及文件全集 | 中（主上下文+1次） |
| 检查返回有无"等/其他/省略"字样 | 子 Agent 自己暗示的缺漏 | 低 |

#### 策略 D：执行反馈循环（最可靠的兜底）
**逻辑**：不追求事前查全，在执行阶段让缺漏自然暴露。
- ✅ 最可靠：代码调用关系强制暴露遗漏。
- ❌ 是事后发现：返工成本高。
- ❌ 对"不涉及代码改动的分析任务"无效。

### 2.3 完备性校验决策流程

```
主 Agent 收到检索子 Agent 返回
   │
   ├─ 策略 A 需求覆盖度：返回能否满足任务需求？
   │    ├─ 能 → 继续 B
   │    └─ 不能（缺环节）→ 补充检索该环节
   │
   ├─ 策略 B pmem 交叉验证：返回覆盖了图谱相关实体吗？（仅 pmem 场景）
   │    ├─ 覆盖 → 继续 C
   │    └─ 漏了图谱实体 → 补充检索该实体相关
   │
   ├─ 策略 C 结构探查：匹配总数 vs 详述数一致吗？
   │    ├─ 一致（或未详述的不影响任务）→ ✓ 判定完备，进入执行
   │    └─ 不一致且影响任务 → 补充检索未详述部分
   │
   └─ 进入执行后保持警惕（策略 D 兜底）
        遇到未见过的方法/编译错误 → 优先归因为"检索遗漏"→ 补查
```

## §3 复核决策树（主 Agent 复核权）

### 3.1 复核权原则

> **主 Agent 有权对任何检索子 Agent 的返回结果进行复核。** 复核依据是"四维检查发现的破绽"或"完备性疑点"，而非"默认不信"。准确性优先于 token 开销，但不能无依据地全量重读（浪费）。

这与原生 ZCode 的"禁止自查"规则明确不同——**在检索类任务上，主 Agent 保留复核权**（见 `SKILL.md` §4.4）。

### 3.2 复核决策树

```
主 Agent 完成四维可信度检查（§1）+ 完备性校验（§2）
   │
   ├─ 全部通过（无破绽、无不完备疑点）
   │    → ✓ 采信，进入下一步（执行/方案制定）
   │
   ├─ 发现局部破绽（某 1-2 点可疑）
   │    → 选择复核粒度：
   │       ├─ 定点复核（§3.3）：只查可疑点的具体行
   │       └─ 补充检索（§3.3）：要求子 Agent 补查缺口项
   │
   ├─ 发现整体不可信（多处矛盾/证据极弱/与已知严重冲突）
   │    → 全量复核（§3.3）：主 Agent 亲自 Read 或重派子 Agent
   │
   └─ 发现子 Agent 失败（返回空/报错/超时）
        → 走 L1/L2/L3 错误处理（见 SKILL.md §4）
```

### 3.3 三种复核粒度

| 粒度 | 适用场景 | 谁做 | 成本 | 示例 |
|---|---|---|---|---|
| **定点复核** | 只查可疑的某 1-2 点 | 主 Agent 自己 Read 那几行 | 低 | 子 Agent 说"mothed 是键名"，主 Agent Read 那一行原文确认 |
| **补充检索** | 完整性不足（缺某些项）| 派检索子 Agent 补查 | 中 | 子 Agent 只查了 controller 没查 mapper → 派子 Agent 补查 mapper 层 |
| **全量复核** | 整体不可信 | 主 Agent Read 全文 或 重派子 Agent | 高 | 子 Agent 返回多处矛盾 + 证据极弱 → 重头来 |

**关键原则**：复核粒度应匹配破绽严重程度，避免无脑全量重读。

### 3.4 复核后的处置

| 复核结果 | 处置 |
|---|---|
| 复核确认子 Agent 正确 | 采信，记录"已复核" |
| 复核发现子 Agent 有误 | 以主 Agent 复核结果为准，记录差异 |
| 复核发现子 Agent 部分对部分错 | 采信对的部分，补查错的部分 |

## §4 能力边界声明（诚实承认）

【完备性校验的能力边界】
1. 主 Agent 无法在事前 100% 可靠判断子 Agent 返回是否完备。
2. 策略 A/B/C 能提高发现缺漏的概率，但不保证消除缺漏。
3. 策略 D（执行反馈）是最可靠兜底，但是事后的。
4. pmem 图谱交叉验证（策略 B）受图谱完备度限制——图谱未记录的关系发现不了。
5. 当主 Agent 遇到"不知道全集"的场景，应默认子 Agent 返回可能不完备，并主动寻找遗漏信号（图谱邻居未覆盖、Grep 匹配数不一致、返回出现"等/其他"字样）。
